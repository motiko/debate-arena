# CLI Venue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Member starts and follows Debates on the live platform from a terminal: `pnpm debate start "Motion" --for a/x --against b/y`. The command authenticates with a personal API token the Member creates on their account page.

**Architecture:**
- **API tokens:** Better Auth's API-key plugin (`@better-auth/api-key`) stores tokens hashed in D1. Members create, list and revoke them on `/account` through the plugin's endpoints, using their session cookie.
- **Token sign-in:** the API accepts `Authorization: Bearer <token>` only where a CLI needs to act as the Member, namely starting a Debate and `GET /me`. Everything else stays session-only, so a leaked token can't vote, report, moderate, export data or manage tokens.
- **The CLI:** a platform client (ADR 0002), `packages/cli`, run directly by Node 24 (type stripping, no build). It uses the typed `packages/api-client`, reads Debates the way a signed-out Viewer does, and follows them over the existing live WebSocket. The connection code moves from `apps/web` into `packages/api-client`, so both Venues share it.

**Tech Stack:** as earlier plans (Hono, D1, Better Auth 1.7.23, Astro 7 + Svelte 5, Vitest 5, Playwright), plus `@better-auth/api-key@1.7.23` (exact pin, peer `better-auth ^1.7.23`). The CLI uses Node 24 built-ins only: `node:util` `parseArgs`, global `fetch`, global `WebSocket`.

**Spec:** no separate design doc. The decisions are this plan's Architecture and Global Constraints, plus ADR 0002 ("The CLI is a platform client, not a standalone local runner"; the CLI links to the web to vote), GLOSSARY "Venue", and the research notes below.

**Research notes (from `@better-auth/api-key@1.7.23` source, 2026-11-15):**
- **Imports:** server `import { apiKey } from '@better-auth/api-key'`. It is not in `better-auth/plugins` at 1.7.23.
- **Table:** `apikey`. `referenceId` holds the user id and has no foreign key.
- **Storage:** keys are stored as a SHA-256 base64url hash, `start` keeps the first 6 characters, and the plaintext key is returned only by create.
- **Endpoints:** `POST /api/auth/api-key/create` (`name`, `expiresIn` in seconds); `GET /api/auth/api-key/list` (no `key` field); `POST /api/auth/api-key/delete` (`{ keyId }`).
- **Verifying:** server-only `auth.api.verifyApiKey({ body: { key } })` returns `{ valid, error, key }`, and `key.referenceId` is the user id.
- **Defaults to override:** the per-key rate limit is on at **10 requests per 24 h**, and keys never expire.
- **`enableSessionForAPIKeys`:** off by default. Leave it off: with it on, a key becomes a full session, which could manage keys and vote.

## Global Constraints

- **Header:** `Authorization: Bearer <token>`. The CLI reads the token from the env var `DEBATE_ARENA_TOKEN` and never from a file or a flag (a flag would land in shell history).
- **Base URL:** `DEBATE_ARENA_URL`, default `https://debate-arena-web.motiko.workers.dev` (production `BETTER_AUTH_URL`; web and API share that origin). The Debate page is `${base}/debates/${id}` and the account page `${base}/account`.
- **Token format:**
  - prefix `da_` (recognisable in leaks and by secret scanners);
  - expiry chosen at creation: 30, 90 or 365 days, default 90;
  - no per-key rate limit: Quota (3 points a day) already caps what a token can spend.
- **Token name:** required, 1–50 characters.
- **Where a token signs in:** `POST /api/debates` and `GET /api/me` only. A session cookie always wins over a token. An invalid, revoked or expired token, or an empty or malformed `Authorization` header, means "no Member" (401), never 500.
- **The CLI never prints the token,** neither in errors nor in `--json` output.
- **The CLI can't vote.** It prints the Debate's web URL for reading and voting (ADR 0002).
- **Exit codes:**
  - `0` success;
  - `1` failure: API error, refused token, a followed Debate failed or was Blocked;
  - `2` usage error.
- **GDPR (ADR 0005):**
  - A Member's export lists their tokens' `name`, `start`, `createdAt`, `expiresAt` and `lastRequest`, never the hash.
  - Account deletion deletes their tokens.
  - The privacy policy mentions API tokens.
- **Not in this plan:**
  - Device-flow login (`debate login`);
  - an npm-published CLI;
  - voting from the CLI;
  - token scopes beyond the fixed route list;
  - a cap on tokens per Member.
- **Tooling and attribution:** as before (oxlint, no formatter). Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A token used anywhere else:** voting, Reports, moderation, `/me/export` and the plugin's own key endpoints must treat a Bearer token as signed out. Owner: Task 2 `a token cannot vote, report, moderate, export or manage tokens`.
2. **Bad tokens as 500s:** `Bearer ` with nothing after it, `Bearer da_garbage`, a revoked key, an expired key, and `Basic xyz` must all give 401 with the usual JSON error. Owner: Task 2 `bad tokens are 401`.
3. **Events lost between loading and connecting, or across a reconnect:** a Turn written after `GET /debates/:id` but before the socket opens, or while it reconnects, must still be printed exactly once. Owner: Task 6 `a Turn written before the socket opens is printed once` and `after a reconnect, missed Turns are fetched`.
4. **Piped output:** `debate start … | tee log` (not a TTY) must contain each Turn once, whole, with no partial drafts or control characters. Owner: Task 6 `without a TTY, only finished Turns are printed`.
5. **The token in CLI output:** an API error, a network failure or `--json` must never echo `DEBATE_ARENA_TOKEN`. Owner: Task 5 `the token never appears in output`.
